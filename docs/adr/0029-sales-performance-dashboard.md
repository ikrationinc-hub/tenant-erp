# 0029 - Sales Performance Dashboard, cached-aggregate refresh (S-6)

## Status

Accepted

## Context

S-1 through S-5 are built, verified, and committed (customer master, lot allocation/costing engine, Sales Order, Delivery, Invoice + Payment Received). Per `docs/SALES-MODULE-PLAN.md`'s build order, S-6 is the final phase: a read-heavy KPI dashboard, explicitly required to run against a cached/pre-aggregated layer rather than live OLTP queries under load.

Two research passes preceded this ADR. The first found that several of the plan's own assumptions didn't hold: `grossProfit()` (`core/inventory-lots/cost-allocation.ts`) had zero callers anywhere in the codebase and no sales table stored a profit figure, contradicting the plan's "from the S-2 costing engine's stored results" wording; no charting library or `core/reporting` module existed; the codebase has never used a Postgres materialized view. The second, done mid-implementation, found that `apps/worker` has **zero dependency on `@ikration/api`** and cannot import `core/reporting/sales-dashboard-refresh.ts` as originally planned - the one established precedent for this exact problem (the contract module's clause-promotion job) solves it by hand-duplicating both the schema subset and the business logic into the worker package.

## Decisions

- **Gross/Net Profit is computed by the refresh job, not read from a pre-existing stored result.** Since nothing computed or stored profit before this phase, the dashboard refresh itself becomes `grossProfit()`'s first real caller: for every sales item with picked lots whose sale falls in the target month, it calls the same pure `costAllocation`/`grossProfit` functions S-2 built (using each lot's real, already-landed `stock_lots.landedRate` plus the sale's own `sales_additional_costs`), and persists the summed result into `sales_dashboard_snapshots.grossProfitUsd`/`netProfitUsd`. Profit is real and decimal-exact, but **only ever computed inside the periodic refresh, never on dashboard load** - satisfying the plan's "not recomputed in the dashboard" intent even though the underlying wiring didn't exist before this phase.
- **Charting**: Recharts added as a new dependency to `apps/web` (explicitly confirmed with the user - CLAUDE.md's "don't add dependencies without asking"). KPI totals stay AntD `Statistic` cards; Customer-wise/Item-wise/Country-wise/Sales-vs-Purchase breakdowns render as Recharts `<BarChart>`s.
- **Aggregate storage**: plain Drizzle-managed cached-aggregate tables (`sales_dashboard_snapshots` + three per-dimension breakdown tables), refreshed by a BullMQ job - not Postgres `MATERIALIZED VIEW`s. The codebase has zero materialized-view precedent (stock-on-hand is deliberately a live `GROUP BY` today, "until proven too slow"); introducing a first-ever materialized view for a 16-week prototype wasn't worth the new migration/Drizzle-modeling pattern this would require.
- **Cache-table audit columns are deliberately skipped.** None of the five S-6 tables use the schema's usual `auditColumns()` (`createdBy`/`updatedBy`/`deletedAt`/`version`) - a documented exception to CLAUDE.md's "every table, no exceptions" convention. Reasoning: (1) no service-account/system-user convention exists anywhere in the codebase for a worker with no `RequestContext` to supply a real `createdBy`, and inventing one just for this table wasn't worth the scope; (2) a pure cache/snapshot row genuinely has no owner, no soft-delete need (it's overwritten in place on every refresh), and no optimistic-locking need (nothing but the refresh job ever writes to it). They get `companyId` + the aggregate figures + `refreshedAt timestamptz` only.
- **`apps/worker` cannot import `apps/api`'s code - the refresh logic is hand-duplicated, mirroring the clause-promotion precedent exactly.** `apps/worker/src/database/tenant-schema.ts` grows a worker-local mirror of every table the refresh touches (`sales`, `salesItems`, `salesPricing`, `customers`, `salesItemLots`, `stockLots`, `stockLotReservations`, `salesAdditionalCosts`, `salesInvoices`, `salesPaymentAllocations`, `contracts`, `purchases`, `purchaseItems`, `purchasePricing`, plus the five new cache tables) - "just what this job touches," per that file's own established convention, not a full schema mirror. `apps/worker/src/sales-dashboard-refresh.ts` is a hand-copied twin of `apps/api/src/core/reporting/sales-dashboard-refresh.ts`'s own KPI derivations, including local re-implementations of `costAllocation`/`grossProfit`/`computeDeliveredStatus` against `decimal.js` directly (no shared wrapper module exists in `apps/worker`, mirroring `contract-generation/placeholder-resolver.ts`'s own inline `Decimal.set(...)` precedent). **Both copies must be kept in sync by hand if the KPI logic changes** - this is real, accepted duplication surface, confirmed with the user as the lower-risk choice versus restructuring the API package to be importable or moving the logic into a new shared workspace package.
- **The API-side `core/reporting/sales-dashboard-refresh.ts` is still real, load-bearing code** - it's exercised by `apps/api`'s own Testcontainers test suite (the only place gross-profit math gets verified against seeded data end-to-end) even though the BullMQ worker never imports it directly. Both copies are tested independently; there is no cross-package test that asserts they stay identical, which is a known limitation of this approach worth revisiting if the two drift.
- **Outstanding Receivables and Shipment Pending are "as of now," not "as of the period."** A receivable stays outstanding regardless of which month its invoice was raised in, and a shipment stays pending regardless of when the sale itself happened - both figures are computed company-wide, independent of `periodMonth`, matching how the credit-exposure warning (ADR 0028) already reads outstanding receivables the same way.
- **Open/Completed Contracts is company-wide, not joined to a specific sale.** `contracts` has no `customerId` column; its only linkage to a sale is a nullable, unconstrained `sourceType`/`sourceId` pair - not a reliable FK to filter or join by. The KPI counts every contract by `status = 'closed'` vs not, with no attempt to correlate a specific contract to a specific sale.

## Consequences

- `sales_dashboard_snapshots`, `sales_dashboard_customer_breakdown`, `sales_dashboard_item_breakdown`, `sales_dashboard_country_breakdown` are four new tables - none audited, all upserted in place by the refresh job, one row per `(companyId, periodMonth[, dimensionId])`.
- `grossProfit()` finally has a real caller after being dead code since S-2 - profit figures are now genuinely computed and verifiable, not aspirational.
- `apps/worker` and `apps/api` now maintain two independent implementations of the same dashboard-aggregation logic. This is consistent with how the contract module's clause-promotion job already works, but it is real technical debt: a future change to the KPI formulas (e.g. switching cost-allocation basis, adding a new breakdown dimension) must be applied in both places, and nothing in CI currently catches a drift between them beyond each package's own independent test suite.
- Recharts is now a real frontend dependency - the first charting library in this codebase.
- No S-7 or further sales-module phases remain per the plan's own six-phase build order; this ADR closes out the Sales module's initial scope.
